The problem

Why browser tests have a bad reputation

await sleep(3000);

The most common line in flaky test suites.

01 · TIMING

The test is faster than the page

So we add sleeps and hope. Too short: it fails. Too long: the suite takes an hour.

02 · SELECTORS

Selectors tied to markup

div > div:nth-child(3) > .btn-x7f2 breaks on the next redesign.

03 · STATE

Tests leak into each other

Test A leaves a cookie behind, test B fails. Only sometimes. Only in CI.

(~1.5 min) Why do people hate UI tests? Three reasons.

Timing. Your script runs faster than the page loads, so people add sleep(3000). Too short and it fails randomly, too long and the suite takes forever. [the line gets crossed out on screen]

Selectors. We grab elements by their HTML position or generated CSS classes. A designer changes the layout and 50 tests break, though nothing is actually broken for the user.

State. Tests share a browser, so cookies or a logged-in session from one test leak into the next.

Playwright was designed specifically to remove all three. Let's see how.

(~1 min) Playwright is an open-source library from Microsoft for controlling browsers with code.

Three engines: Chromium (Chrome and Edge), Firefox, and WebKit, the engine behind Safari. So you can test Safari behaviour even on Windows or Linux.

Four languages. Today I'll use TypeScript, which is the most popular choice and the one that comes with the full test runner.

And it's batteries-included: you don't need to stitch together a runner, an assertion library and a reporter. One install.

Fun fact: the team came from Google, where they built Puppeteer, then moved to Microsoft and built Playwright to fix what they couldn't fix there, mainly cross-browser support.

(~1.5 min) Here's the key architectural idea, in one picture.

Top: classic WebDriver, the original Selenium model. Each command (click, type, find) is a separate HTTP request through a driver. It's like making a phone call for every single action, and to know whether something changed you have to call again and ask.

Bottom: Playwright keeps one connection open, both ways. The browser pushes events: page loaded, request finished, element appeared. That's why Playwright can wait intelligently instead of guessing.

Under that, it talks to each engine in its native language: Chrome DevTools Protocol for Chromium, and patched protocols for Firefox and WebKit that the team maintains themselves.

Being fair: Selenium is evolving too. The new WebDriver BiDi standard brings this two-way model to Selenium. So this isn't about Selenium being bad; it's about the design Playwright started with.

BrowserContext

Like a brand-new incognito window. Created for each test, thrown away after.

No leaked logins, no leftover cookies, so tests can safely run in parallel.

(~1 min) This fixes problem number three, shared state.

Starting a browser is slow, about a second. So Playwright starts it once. Then for every test, it creates a BrowserContext, which is basically a fresh incognito profile: its own cookies, its own local storage, its own cache. Creating one takes milliseconds.

When the test ends, the context is thrown away. Nothing leaks into the next test. And because tests don't share anything, Playwright can run them in parallel.

Bonus: two contexts in one test = two different users. Great for testing a chat between Alice and Bob.

Writing a test

Every test is three steps: go, find, check

tests/todo.spec.ts
import { test, expect } from '@playwright/test';

test('user can add a todo', async ({ page }) => {
  await page.goto('/todomvc');

  const input = page.getByPlaceholder('What needs to be done?');
  await input.fill('Prepare Playwright talk');
  await input.press('Enter');

  await expect(page.getByTestId('todo-item'))
    .toHaveText(['Prepare Playwright talk']);
});
1

Go

page is a fresh tab in a fresh context, handed to you by the runner.

2

Find

Locators describe the element the way a user sees it.

3

Check

Assertions retry until true. Notice: zero sleeps.

(~1.5 min) This is a complete, real test. It runs against Playwright's own demo app, and it's in the demo folder.

Go: we navigate. Where does page come from? The runner gives it to us. That's called a fixture: a fresh tab in a fresh context for every test.

Find: we don't use CSS paths. We say "the field with placeholder 'What needs to be done?'", exactly like a human would describe it.

Check: expect with await. This is a web-first assertion: it keeps retrying until the text appears or the timeout hits. Look at the whole test: not a single sleep.

Assertions too

await expect(x).toBeVisible() retries for up to 5 seconds by default.

(~1.5 min) This is the feature that kills flaky tests: auto-waiting.

When you write .click(), Playwright doesn't click immediately. It first checks: is the button visible? Is it stable, not in the middle of an animation? Is it enabled? Will it actually receive the click, or is a cookie banner covering it? [checks light up on screen]

Only when all checks pass does it click. If something isn't ready, it keeps retrying. If it times out, the error tells you exactly which check failed, e.g. "element is covered by div.cookie-banner".

Assertions work the same way. So: delete your sleeps.

Locators

Find elements like a user, not like the DOM

fragilepage.locator('#root > div:nth-child(3) > button.btn-x7f2')

Breaks as soon as someone touches the layout or CSS.

resilientpage.getByRole('button', { name: 'Sign in' })

Survives redesigns. Matches what users and screen readers perceive.

Recommended order

getByRolebutton, link, heading…
getByLabelform fields
getByText · getByPlaceholdervisible text
getByTestIddata-testid contract
CSS / XPathlast resort

Bonus: locators see inside open Shadow DOM automatically, no special syntax.

(~1.5 min) Problem number two: selectors.

On the left, the old way: a CSS path through the DOM. It works today and breaks the moment someone wraps that button in another div.

The Playwright way: getByRole('button', {name: 'Sign in'}). "The button called Sign in." That doesn't change when the CSS changes, only when the user experience changes, and then the test should fail.

On the right, the recommended priority. Role first, then label, then text. Test IDs when nothing else is stable. CSS and XPath only as a last resort.

Nice side effect: if getByRole can't find your button, a screen reader probably can't either. Your tests push you toward accessible UI.

Pro tip: you don't have to guess locators. UI mode and codegen have a locator picker: hover an element and it gives you the best locator.

(~2 min) Don't explain all six in depth; pick two and go fast through the rest.

Mock any API: Playwright can intercept network requests and answer them itself. Frontend not blocked by backend; you can also simulate a 500 error to see if your error page works. I'll show this live.

Log in once: logging in through the UI is slow. Do it once in a setup step, save the session to a JSON file, and every test starts already logged in.

Devices: there's a built-in list of phones with viewport, touch and user agent. You can also fake GPS location, timezone and language.

Visual: compare screenshots to a saved baseline, and mask things like timestamps.

Parallel: workers by default, and sharding to split across CI machines.

Every browser: list them as projects in the config; the same test runs on all three.

(~1.5 min) A test failed in CI at 3 a.m. What happened? Logs aren't enough.

Playwright records a trace: every action, a DOM snapshot before and after each step, network requests, console logs, and the source line. You open it in the Trace Viewer and scroll through time.

In this example, the click timed out. In the snapshot we can see why: a cookie banner covers the button. The error message says the same: the cookie-banner div "intercepts pointer events". That's auto-waiting telling you which check failed.

It's a zip file. Download it from CI, open it locally or drag it onto trace.playwright.dev; it runs entirely in your browser.

(~1.5 min) If you want an AI to use a website, you have to describe the page to it. Option one: give it the raw HTML. On the left is a real piece of GitHub's HTML. That whole block is one hamburger icon. The full page is over 400,000 characters, and almost none of it means anything to the AI. Every character costs tokens, money and attention.

On the right: the ARIA snapshot, the accessibility tree that screen readers use. Just roles and names: a navigation, a link called Code, a heading. That's what the AI needs to decide what to do.

These numbers are real: I measured them with the demo test you just saw. About eight times less text, and it's all signal. (On a lean page like playwright.dev it's closer to 2×; the heavier the app, the bigger the win.)

The [ref=e84] bits are IDs the agent uses to say "click this one". Same idea as getByRole: good locators for humans are good locators for AI.

(~1.5 min) So how does it fit together? Through MCP, the Model Context Protocol, a standard way for AI models to call tools.

The loop: Observe: Playwright gives the model an ARIA snapshot. Think: the model decides "I need to click Get started". Act: it sends a tool call, browser_click with the ref. Execute: Playwright performs it, with all the auto-waiting we talked about. Then observe again. Repeat until the task is done.

On the right, two things you can try today. npx playwright mcp starts the official MCP server, built into Playwright, and you connect it to an AI assistant.

And init-agents sets up three test agents: a planner that explores your app and writes a test plan, a generator that turns it into Playwright tests, and a healer that tries to fix tests when they break.

Realistic note: these are helpers. A human still reviews what they write.

(~45 s) If you forget everything else, remember three things.

One: let Playwright wait. If you see a sleep in a test, it's a bug waiting to happen.

Two: locate like a user. getByRole first. Your tests get stable and your app gets more accessible.

Three: when something fails, open the trace. It shows you what happened instead of making you guess.
